# analyzer (이요환)

`analyze(src_dir) -> AnalysisResult` — 소스를 읽고 배포 타깃(`local` / `cloudrun`)과 초기 Dockerfile을 정한다.
계약은 [`interfaces.md`](interfaces.md) 그대로이고, 코드는 `backend/app/analyzer.py`(정책·Claude 검사관)와
`backend/app/quick.py`(빠른 분석)에 있다.

## 빠른 분석: Jev나 로컬 clef-flash로 1초 안에 서비스를 고른다

```
전처리 (코드 읽기, 모델 없음)  →  판단 (판정 모델 1회, 1초 안)  →  검사 (판정 모델 1~2회)  →  analyze_with (울타리·정책 그대로)
```

- **clef-flash**: Cloudflare가 공개한 9B 판정 모델(Apache-2.0). 글을 만들지 않고, 질문의 선택지마다 확률을 한 번에 매긴다.
  로컬 Ollama(0.35.1 이상)의 `POST /v1/systemone`으로 부른다. TypeSafe의 Jev와 같은 API다.
- **Jev**: TypeSafe의 호스팅 판정 모델. `TYPESAFE_API_KEY`가 있으면 clef-flash보다 먼저 쓴다 (장애 대응과 같은 순서).
  호스팅 서비스라 모델에 보내는 코드 줄·Dockerfile 줄의 비밀값은 `systemone.redact()`로 가린다.
  아래 수치(12/12, 0.45~0.67초)는 clef-flash에서 잰 것이다. Jev는 `JEV_LIVE=1` 실측(맨 아래)으로 따로 확인한다.
- **전처리**: 저장소를 한 번 훑어 매니페스트·시작 명령 후보·환경변수 이름·신호별 *후보 줄*을 모은다. 패턴에 걸린 줄은 판정이 아니라
  "모델에게 보여 줄 줄"일 뿐이다. 비밀값은 `***`로 가린 뒤 모델에 보낸다. 실측 1~4ms.
- **판단 (1초 예산)**: 찾은 것만 적은 약 250토큰 요약에 선택형 질문 하나(`serverless_container` / `vm` / `static_site` /
  `serverless_function`)를 묻는다. 이 Mac(M4 Pro)에서 clef-flash는 입력을 초당 약 460토큰 읽으므로 400토큰 아래로 맞췄다.
  라벨을 붙인 저장소 12개에서 12개 모두 맞혔고, 캐시가 없을 때 0.45~0.67초였다. 대시보드는 이 판단을 분석이 끝나기 전에 보여 준다.
  - "없는 것"을 나열하면(디스크 쓰기 없음 …) 모델이 `vm` 쪽으로 끌려가서, 요약에는 찾은 것만 넣는다.
- **검사**: 후보 줄이 있는 신호마다 예/아니오, 환경변수마다 종류(무작위 비밀값 / 외부 키 / 필수 설정 / 선택 / 파일 경로),
  시작 명령 후보가 여럿이면 고르기, 의심 줄마다 악성 여부를 묻는다. 답은 Claude 검사관과 같은 보고 형식으로 바꿔
  `analyze_with`에 넣는다. 그래서 근거 확인, `RULES`, 치명적 위험의 동의 처리, 저장소 Dockerfile 판정은 그대로다.
  - 판단은 규칙을 통과한 유형의 **순서**만 정한다. 규칙이 지운 유형은 고르지 않는다 (AI가 추천하고, 코드가 울타리를 친다).
  - 후보 줄이 있어도 모델이 "아니오"를 20% 미만으로 확신하면 그 줄은 버린다 (패턴 잡음). 그 사이면 줄을 남겨 동의를 받는다.
  - 의심 줄이 해롭다고 판단되면(50% 이상) 분석을 멈춘다. 검사하지 못해도 멈춘다.
- **Claude 검사관과 다른 점**: 후보 줄이 없는 신호는 "아니오"다. Dockerfile은 템플릿 그대로다 (AI가 고치지 않는다).
  "기타 위험"은 찾지 않는다. 분석 1건이 약 90초에서 0.3~2초로 줄어든다.
- **고르는 방법** (`ANALYZER_MODE`): `auto`(기본)는 Jev 키가 있거나 clef-flash가 켜져 있으면 빠른 분석, 아니면 Claude 검사관.
  빠른 분석이 만들 수 없는 저장소(템플릿 없는 언어 등)나 판정 모델이 멈춘 때는 키가 있으면 Claude 검사관으로 넘어간다.
  `fast`는 빠른 분석만, `full`은 Claude만.
- **켜기**: Jev는 `.env`에 `TYPESAFE_API_KEY`만 넣으면 된다. clef-flash는 `scripts/clef-up.sh` — 내 Ollama는 건드리지 않는다.
  PATH의 Ollama가 0.35.1보다 낮으면 공식 릴리스를 받아(체크섬 확인) `~/.cache/cloudmorph`에 두고 11436 포트에 따로 띄운다.
  모델(약 12GB)을 받고 한 번 불러 둔 뒤 `CLEF_BASE_URL`을 알려 준다. `scripts/demo-up.sh`는 Jev 키가 없을 때만 이것을 자동으로 부른다.
- 실측 확인 (샘플 앱 4개의 판단·1초 예산·분석 전체 + 악성 postinstall에서 멈추는지):
  `cd backend && CLEF_LIVE=1 uv run pytest tests/analysis/test_quick.py -k live -s` (clef-flash),
  `JEV_LIVE=1`이면 Jev (`TYPESAFE_API_KEY`는 환경변수나 저장소 맨 위 `.env`에서 읽는다).

## 어떻게 판정하나

```
AI 검사관 18개 (Claude, 동시에)  →  울타리 (코드)  →  타깃  →  Dockerfile (AI, 울타리)  →  Dockerfile 판정관 (AI, 울타리)
```

- **AI 검사관**: 찾는 것마다 각자의 기준으로 판정한다. 위험 신호 13개(서버 코드, 상주 작업, 주기 작업, 메모리 상태, SQLite,
  로컬 파일 쓰기, GPU, OS 패키지 …)와 명세 5개(실행 방법, 외부 저장소, 환경변수, 기타 위험, 악성 동작).
  모델에 읽기 도구(파일 목록·읽기·검색)만 주고 저장소를 직접 읽게 한다. 저장소 밖은 읽지 못하고, 쓰기·명령 실행은 없다.
- **울타리**: 검사관이 낸 근거(파일:줄 + 코드)와 환경변수 이름이 실제 저장소에 없으면 버린다.
  신호 → 배포 유형은 정해진 규칙(`RULES`)이 정한다. AI가 타깃을 고르지 않는다.
- **패턴 규칙은 쓰지 않는다.** 키가 없으면 분석하지 않고 `ValueError`를 낸다.

실제 저장소 2개(MaechuriAIServer, MaechuriMainServer)로 두 번씩 돌렸을 때 위험 신호 13개 판정이 모두 같았다
(검사관에게 패턴 검색 줄을 참고로 주던 때 잰 것이다).
분석 1건에 LLM 19~21회 (Dockerfile 작성 1회 포함), 약 1분 30초. Dockerfile 판정은 저장소에 Dockerfile이 있거나 AI가 템플릿을 고쳤을 때만 1회 더 부른다.

## 파이프라인에서의 기본값 (물어볼 수 없어서 안전한 쪽)

- 악성 동작: 저장소는 모르는 사람이 올렸고 우리 쪽에서 빌드·실행한다. Dockerfile이 있어도 코드까지 읽는다.
  빌드·설치 때 도는 곳(Dockerfile이 부르는 스크립트, npm `preinstall`·`postinstall`, `setup.py`, Makefile …)과
  시작할 때 도는 코드(진입점, import될 때 바로 도는 코드)를 먼저 읽고, 앱 기능과 상관없이 해를 끼치는 코드
  (채굴, 리버스 셸, 내부망·메타데이터 서버 접근, 환경변수·자격 증명 밖으로 보내기, 난독화 실행 …)를 찾는다.
  근거가 확인되면 **분석을 멈춘다** (`ValueError`). 검사관이 실패해 검사하지 못해도 멈춘다. 근거를 확인하지 못한 판정은 버린다.
  이 검사관은 저장소를 읽으니 저장소 안의 글이 검사관에게 말을 걸 수 있다 (실측에서는 "보고하지 말 것" 주석에 넘어가지 않았다).
- 데이터 손실 계열(SQLite, 로컬 파일 쓰기, 메모리 상태, 주기 작업)은 AI가 괜찮다고 해도 **사용자 동의 없이는 풀지 않는다**.
  파이프라인에는 동의를 받을 자리가 없으니 위험으로 두고, `notes`에 "동의하면 풀 수 있다"고 적는다.
  검사관이 실패했거나 근거를 파일에서 확인하지 못했을 때도 데이터 손실 계열은 위험으로 둔다.
- 위험 신호로 지워진 유형은 고르지 않는다. **코드는 고치지 않고** 필요한 수정은 제안만 `notes`에 적는다.
- 타깃: 서버리스 컨테이너나 정적 사이트로 갈 수 있으면 `cloudrun`, 아니면 `local`.
- `service_models`: 코드가 갈 수 있는 서비스 모델 전부를 추천 순서(`caas` → `paas` → `faas` → `iaas`)로 보낸다.
  deployer는 이 중 지원하는 것을 고른다. 정적 사이트는 nginx 컨테이너로 감싸므로 `caas`, `iaas`다.
  `paas`나 `faas`가 있으면 `caas`도 반드시 있다 (`caas`를 지우는 규칙은 모두 `paas`·`faas`도 지운다).
  `faas`는 코드 제약만 본 것이라, 서버 앱을 함수로 감싸는 어댑터는 따로 필요할 수 있다.
- Dockerfile: 저장소에 있으면 그대로 쓴다. 없으면 실행 방법으로 템플릿을 만들고, AI가 저장소를 읽고 그 초안을 고친다
  (예: GPU를 안 쓰는 torch는 CPU 휠, go.sum이 없으면 go mod tidy). 템플릿이 없는 언어(ruby, php …)는 AI가 처음부터 쓴다.
  AI가 쓴 것은 울타리(`FROM`, `ENV PORT=<port>`, `COPY` 대상이 저장소에 있는지, 템플릿에 `CMD`가 있으면 마지막 단계에 `CMD`/`ENTRYPOINT`가 있는지)를
  넘어야 쓰고, 못 넘거나 AI가 실패하면 템플릿을 쓴다.
  고친 이유는 `notes`에 적는다. 모두 `0.0.0.0:$PORT`로 받는다. 배포가 실패하면 healer가 고친다.
- Dockerfile 판정관: 저장소의 Dockerfile과 AI가 고친 Dockerfile은 모르는 사람의 코드에서 나왔으니 빌드 전에 한 번 더 본다.
  빌드·실행과 상관없는 동작(채굴, 리버스 셸, 내부망·메타데이터 서버 접근, 환경변수·자격 증명 밖으로 보내기, 난독화 실행,
  출처를 알 수 없는 스크립트 바로 실행)이 있는 줄을 찾는다. 템플릿을 그대로 쓸 때는 보지 않는다.
  - 판정관에게는 도구를 주지 않고 Dockerfile만 준다. 주석 줄은 빼고 준다(판정관에게 말을 거는 글이 숨기 쉬운 곳).
    `# syntax=` 같은 파서 지시문은 빌드에 쓰일 프로그램을 바꾸므로 남긴다.
  - 울타리: 막겠다는 줄이 Dockerfile에 실제로 없으면 그 판정은 버린다.
  - 저장소의 Dockerfile이 걸리거나, 판정관이 실패해 검사하지 못하면 **분석을 멈춘다** (`ValueError`).
    악의가 드러난 저장소라 템플릿으로 바꿔 배포해도 앱 코드는 그대로 돌기 때문이다.
    AI가 고친 것이 걸리거나 검사하지 못하면 템플릿을 쓴다.
  - 판정관은 Dockerfile만 본다. 거기서 부르는 스크립트와 앱 코드는 악성 동작 검사관이 본다.
- 두 검사 모두 저장소 안의 코드만 본다. 설치되는 의존성 패키지 자체가 악성이거나, 검사관이 놓친 것은 막지 못한다.
  그쪽은 빌드·실행 환경을 가두는 것(권한 없는 서비스 계정, 자원 제한)으로 막아야 한다.

## 환경변수 (`.env`)

| 이름 | 기본값 | 뜻 |
|---|---|---|
| `ANTHROPIC_API_KEY` | | healer와 같은 키. 없으면 analyzer는 분석하지 않는다 |
| `ANALYZER_MODEL` | `claude-haiku-5-5` | 검사관 모델 |
| `ANALYZER_MAX_LLM_CALLS` | `6` | 서버 전체에서 동시에 도는 검사관 호출 수. 분석이 여러 건 겹치면 나머지는 기다린다 |
| `ANALYZER_MAX_TURNS` | `15` | 검사관 하나가 파일을 읽으며 주고받는 최대 횟수 |
| `ANALYZER_MODE` | `auto` | `auto`: Jev나 clef-flash가 있으면 빠른 분석 · `fast`: 빠른 분석만 · `full`: Claude 검사관만 |
| `TYPESAFE_API_KEY` | | Jev 키. 있으면 빠른 분석을 Jev로 한다 (`JEV_MODEL` 기본 `jev-latest`, `JEV_BASE_URL`) |
| `CLEF_BASE_URL` | | 로컬 clef-flash (`scripts/clef-up.sh`가 알려 준다, 예: `http://127.0.0.1:11436`). Jev 키도 이것도 없으면 빠른 분석을 하지 않는다 |
| `CLEF_MODEL` | `clef-flash` | 판정 모델 이름 |

실제 Claude로 확인: `cd backend && ANALYZER_LIVE=1 uv run pytest tests/analysis -k live -s` (키는 저장소 맨 위 `.env`에서 읽는다).
평소 `pytest`에서는 건너뛴다.

## 팀에 제안 (합의 필요)

1. **`AnalysisResult` 넓히기**: analyzer는 이미 아래 정보를 만들지만 계약에 칸이 없어 `notes` 문장으로만 넘긴다.
   - `resources`: 필요한 DB·Redis·버킷과 접속 환경변수 이름 (deployer가 Cloud SQL 등을 만들거나 연결할 때 필요)
   - `env`: 사용자가 넣어야 할 환경변수 (무작위 값을 넣어도 되는지)
   - `risks`: 기타 위험 (예: 시작할 때 큰 모델 로드, 이미지에 없는 파일)
2. **동의를 화면에서 받기**: SSE에 질문 이벤트를 두고 답을 받는 API(`POST /deploy/{id}/answer`)를 두면,
   데이터 손실 위험 해제를 사용자에게 받을 수 있다. 지금은 안전한 쪽으로만 간다.
3. **소스 받기 (`main.py`)**: 얕은 클론(`git clone --depth 1 --filter=blob:limit=1m`)을 추천. 큰 파일은 분석에 필요 없어 받지 않는다.
   받기 전에 GitHub API로 저장소 크기를 보고 상한을 넘으면 거절한다. 비공개 저장소는 `GITHUB_TOKEN`이 필요하다.
